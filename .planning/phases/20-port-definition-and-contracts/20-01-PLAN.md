**File 4: `INotificationService.cs`** (per D-01, D-02, D-03, D-04, D-05)
```csharp
namespace Ray.BiliBiliTool.Application.Contracts.Notifications;

/// <summary>
/// 通知服务端口 — 应用层通过此接口发送通知，不关心底层是 Serilog 还是 Telegram HTTP
/// </summary>
public interface INotificationService
{
    /// <summary>
    /// 发送单条事件通知
    /// </summary>
    /// <param name="message">通知消息</param>
    /// <param name="groupKey">批次分组键（通常是 fireInstanceId）</param>
    Task SendAsync(NotificationMessage message, string groupKey);

    /// <summary>
    /// 发送任务完成摘要
    /// </summary>
    /// <param name="title">摘要标题（通常是任务名称，如 "Daily"）</param>
    /// <param name="lines">摘要行列表</param>
    /// <param name="groupKey">批次分组键（通常是 fireInstanceId）</param>
    Task SendSummaryAsync(string title, SummaryLine[] lines, string groupKey);
}
```

Key decisions implemented:
- D-01: Two async methods — `SendAsync` and `SendSummaryAsync` (no `FlushAsync`)
- D-02: `FlushAsync` deliberately excluded — flushing is `BatchSinkManager`'s concern
- D-03: `groupKey` is an explicit parameter on both methods, not ambient LogContext
- D-04: `NotificationMessage` is a record with Title, Body, Level, optional GroupKey
- D-05: `SummaryLine` is a record with Label, Value, optional StatusIcon
- D-06: `NotificationLevel` is an enum with Info, Warning, Error (NOT Serilog's LogEventLevel)
- D-07: `NotificationMessage` and `SummaryLine` are completely separate types

Do NOT add `FlushAsync` to the interface. Do NOT reference `Serilog`, `ILogger`, or any Infrastructure type. Do NOT modify the `.csproj` — the new files are in a subfolder of the existing project and will be picked up automatically.
