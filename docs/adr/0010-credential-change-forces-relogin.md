# ADR-0010：凭据变更成功后一律强制重新登录

- 状态：已接受
- 日期：2026-09-29
- 关联：ADR-0009、`src/Ray.BiliBiliTool.Web/Components/Pages/Admin.razor`（`.cs`）

## 背景

ADR-0009 拆开改名与改密时，只给**改名**加了强制重新登录：改密成功仅弹一条 Snackbar，会话继续沿用。

结果是同一个页面里两个操作的行为不一致，而用户看到的差别没有道理可讲——两项都是「凭据变更、都需要当前密码确认」，一个会把你踢出去，另一个不会。用户直接把这一点当成了 bug 报回来。

技术上两者都有同一个事实：**当前会话是用旧凭据建立的**。

- 改名：Cookie 里的 `ClaimTypes.Name` 直接变成陈旧值，不重新登录就一直不一致。
- 改密：Cookie 不携带密码，所以它仍然有效、技术上能继续用。但「密码已经换了、旧凭据开的会话还开着」正是密码轮换想要消除的状态——改密的动机常常就是「怀疑密码泄露」，此时让旧会话存活违背意图。

## 决策

**改密与改名在成功后走同一条路径**：Snackbar 提示成功 → 延时 1200ms（让提示可读）→ `NavigateTo("/auth/logout", forceLoad: true)`。

两者共用 `Admin.razor.cs` 里的一个私有方法 `SignOutAfterDelayAsync()`，`LogoutDelayMs` 常量只保留一处。延时期间提交按钮保持禁用，避免用户重复提交。

页面文案同步说明这一行为：Hero 副标题写明「成功后当前会话将退出，需重新登录」，改密卡片底部也有一行同样的提示。

## 后果

- 两个操作行为一致，用户不需要记忆两种语义。
- 代价：每次改密都要重新登录，属于刻意打断。可接受——改密不是高频操作，而重新认证的成本远低于留下一个用旧凭据建立的会话。
- 尚未做到的是服务端会话失效：真正的强制下线需要给 `User` 加 security stamp 并在校验时比对，届时可把这里的跳转改成「重签 Cookie + 保留会话」。当前把两处跳转收敛到 `SignOutAfterDelayAsync()`，就是为了那一天只改一个地方。

## 备选方案

**A. 维持改密后不登出。** 改动为零，也说得通（Cookie 确实仍然有效）。但两个同类操作行为分裂，且留住了密码轮换本要消除的旧会话。未采纳。

**B. 只弹提示、不跳转，由用户自己决定何时登出。** 用户体验上更温和，但「提示里说建议重新登录」和「真的重新登录」相比，前者基本不会被执行，等于没做。未采纳。

**C. 立即跳转，不给提示延时。** 最干净，但 Snackbar 来不及被看到，用户会以为操作失败或页面出错。1200ms 与改名路径保持一致。未采纳。
